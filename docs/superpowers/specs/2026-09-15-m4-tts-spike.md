# M4 TTS spike — findings

> **Status:** investigation record. **Date:** 2026-09-15. History, not a design and not a contract — it exists so the M4 TTS decisions can be re-examined without redoing the work. Covers milestone M4 in [docs/implementation-plan.md](../../implementation-plan.md). Internal name **HearBook**; user-facing name **Enisma**.
>
> Everything below was measured on one Linux x86_64 machine, Python 3.12.3, **CPU only** (sherpa-onnx `provider="cpu"`, onnxruntime default CPU provider), against these exact versions: `sherpa-onnx` 1.13.8, `sherpa-onnx-core` 1.13.8, `onnxruntime` 1.30.0, `phonemizer` 3.4.0, `espeakng-loader` 0.2.4 (bundling espeak-ng 1.52.0), `uroman` 1.3.1.1, `kokoro-onnx` 0.6.1, `numpy` 2.5.3, `soundfile` 0.14.0. Numbers from other versions or machines are not interchangeable with these.
>
> Models are the four repos named in the M4 kickoff: `onnx-community/Kokoro-82M-v1.0-ONNX`, and `hadamard-2/mms-tts-{amh,tir,orm}-onnx`.

## Verdict

All four languages synthesize correctly, and the dependency footprint is small — **203 MB** of Python packages, against the 1.4 GB docling would have cost. There is no torch anywhere in this pipeline.

Two things are materially worse than the implementation plan assumes, and both are UX problems rather than feasibility problems. **Synthesis is slow**: a single textbook page takes 40–100 seconds on CPU, so "preview this page" cannot be a button that blocks until audio arrives. And **the MMS symbol tables have no digits**, so every page number, date, figure number and quantity is currently dropped silently rather than spoken.

One constraint is not technical at all: the three Ethiopian-language models are **CC-BY-NC-4.0**.

## What was proven end to end

Real audio, written to disk and non-silent (RMS reported per run), for all four languages:

| Language | Engine | Model | Output |
| --- | --- | --- | --- |
| English | Kokoro via onnxruntime + espeak-ng G2P | `model.onnx`, 326 MB | 24 kHz, 54 voices available |
| Amharic | MMS VITS via sherpa-onnx + uroman | `mms-amh`, 114 MB | 16 kHz, single speaker |
| Tigrigna | MMS VITS via sherpa-onnx + uroman | `mms-tir`, 114 MB | 16 kHz, single speaker |
| Afaan Oromo | MMS VITS via sherpa-onnx + uroman | `mms-orm`, 114 MB | 16 kHz, single speaker |

The MMS models are genuine sherpa-onnx exports — `model.onnx` carries the metadata sherpa-onnx reads (`model_type=vits`, `frontend=characters`, `n_speakers=0`, `sample_rate=16000`) alongside a `tokens.txt` symbol table. The recipe in `../amharic-speech-models/tts/mms.py` transfers to all three languages unchanged apart from the `lcode` passed to uroman.

The Kokoro repo is self-contained for the raw-onnxruntime path: `onnx/model.onnx` (inputs `input_ids`, `style`, `speed`), `voices/*.bin` style vectors, and `tokenizer.json` carrying the full 115-entry phoneme vocabulary. Nothing needs to be fetched from `hexgrad/Kokoro-82M` at runtime. On the test sentence every espeak phoneme mapped into the vocabulary — zero unmapped characters.

## Speed — this is the M4 design problem

Measured on CPU, `num_threads=2` for sherpa-onnx, onnxruntime defaults for Kokoro. RTF is synthesis time ÷ audio duration; below 1.0 means faster than real time.

Single sentences:

| Language | Input | Synth | Audio | RTF |
| --- | --- | --- | --- | --- |
| Amharic | 175 romanized chars | 5.45 s | 11.24 s | 0.485 |
| Tigrigna | 192 romanized chars | 7.74 s | 8.97 s | 0.863 |
| Oromo | 166 romanized chars | 8.12 s | 9.57 s | 0.849 |
| English | 156 phoneme tokens | 2.98 s | 9.60 s | 0.311 |

Page-length, which is the number that actually matters — M3 measured real textbook pages at 519–2948 characters:

| Case | Input | Synth | Audio | RTF |
| --- | --- | --- | --- | --- |
| English page | 1473 chars → 1586 tokens → 4 chunks | **41.6 s** | 92.4 s | 0.45 |
| Amharic page | 2000 chars → 3511 romanized chars, one utterance | **99.1 s** | 211.0 s | 0.47 |

**A full page takes 40–100 seconds to synthesize.** The existing UI fakes it with a 4.5-second timer in [editor.tsx:439](../../../src/components/editor/editor.tsx:439). Whatever replaces that needs progress, cancellation, and caching — the same shape of problem M3 hit with extraction, and it is bigger than the plan's "wire settings preview + per-page audio" line suggests.

Note this is the time to synthesize the *whole* page, not the time before the first sound: both engines can emit sentence-sized pieces as they go, putting first audio at roughly 7–10 seconds. See the segmentation section below.

Extrapolating to the 171-page Biology textbook M3 used as its fixture, and assuming pages resemble the ones measured: **roughly 2 hours for English, roughly 4.7 hours for Amharic**. That is an M5 problem, but it is created here, and it is the strongest argument for caching per-page audio to `pages.audio_path` as M4 synthesizes rather than re-synthesizing at export.

Ge'ez romanization inflates the character count: 2000 Amharic characters became 3511 Latin characters, a factor of 1.76. uroman itself is free — 3.3–7.2 ms per sentence, and a one-time 2.23 s table build at load.

## Digits are silently dropped — a real quality bug inherited from the reference

All three MMS symbol tables are Latin-only. Full contents, 52–54 tokens each: `a–z`, `A–Z` folded to the same ids, apostrophe, hyphen, and a space/blank. **No digits, no punctuation.**

The reference implementation strips everything outside `[A-Za-z'\s]` to stop sherpa-onnx emitting per-character warnings. That is correct for the model and wrong for a textbook:

```
in : ምዕራፍ 3 ገጽ 47 ላይ 1985 ዓመት ተጻፈ።
out: meeraafe gatse laaye aamate tatsaafa

in : Boqonnaa 3, fuula 47, bara 1985 barreeffame.
out: Boqonnaa fuula bara barreeffame
```

Every number vanishes. For a chat server that is a rounding error; for an audiobook of a school textbook it means chapter numbers, page references, dates, quantities and equation numbers are all simply not spoken. Fixing it needs number-to-words per language — and Amharic and Tigrigna number-to-words is not a library call away.

English does not have this problem — espeak-ng expands numbers itself before phonemization.

**Not stripping does not help.** Passing digits through to the model unchanged was tested directly: sherpa-onnx's character frontend logs `Skip unknown character. Unicode codepoint: \U+0033` per digit and speaks the rest. The audio is equivalent to the stripped version apart from slightly longer pauses where the digits were (2.85 s vs 2.59 s for the same Amharic sentence). The choice is not "strip or don't" — it is "convert numbers to words, or accept that numbers are not read aloud". Stripping only buys a quiet stderr.

**One useful simplification: uroman normalizes Ge'ez numerals to Latin digits.** `ምዕራፍ ፫ ገጽ ፵፯` romanizes to `meeraafe 3 gatse 47`. Both numeral systems therefore arrive at the same place — but only *after* romanization, which is too late to convert them to words in the source language. See the ordering problem below.

### num2words2 covers all three languages, with two caveats

`num2words2` 1.0.20 (PyPI; a Rust-backed fork of `savoirfairelinux/num2words`, declaring `LGPL-2.1-only` in its installed metadata) was installed and tested. It adds **7 MB** to the environment. All three languages convert:

| Lang | 3 | 47 | 1985 | Script |
| --- | --- | --- | --- | --- |
| `am` | ሦስት | አርባ ሰባት | አንድ ሺህ ዘጠኝ መቶ ሰማንያ አምስት | **Ge'ez** |
| `ti` | seleste | arba'a n shew'ate | shiḥ n tish'ate mi'ti n semanya n ḥamushte | **Latin** |
| `om` | sadii | afurtama fi torba | kuma fi sagal dhibba fi saddeettama fi shan | Latin (correct for Oromo) |

**Caveat 1 — Ge'ez numerals are rejected.** `num2words('፫', lang='am')` raises `NotImplementedError: sentence: non-ascii digits`; only `int` input works. Number-to-words must run *before* uroman, so something else has to turn `፫` into `3` first. **uroman itself does this correctly** and is already in the stack — applied to just the numeral run rather than the whole string:

| Input | uroman | abugida 0.3.4 `convert(g, "gz", "ha")` |
| --- | --- | --- |
| `፫` | `3` | `ValueError: substring not found` |
| `፲` | `10` | `ValueError: substring not found` |
| `፵፯` | `47` | `ValueError: substring not found` |
| `፻` | `100` | **`200`** |
| `፲፱፻፹፭` | `1985` | `1985` |

Verified end to end: matching `[፩-፼]+`, romanizing each match on its own to get an integer, converting that to words, then romanizing the whole sentence, produces identical output for Ge'ez and Arabic numerals, and handles both mixed in one sentence.

`abugida` 0.3.4 (MIT, no dependencies) converts Arabic→Ge'ez correctly for everything tested, but the Ge'ez→Arabic direction — the one a reader needs — has two bugs, both in `_split_geez_num`. Its final line is `geez_num.index("፻" if len(arabic_segments) % 2 == 1 else "፼")`, called unconditionally, so **any numeral below 100 raises `ValueError`** because it contains neither character. Separately, a bare `፻` returns 200: the empty leading segment is scored as 1 and multiplied by 100. Since uroman already covers this correctly, abugida is not needed for M4's numeral path.

**Caveat 2 — Tigrinya comes back romanized, not in Ge'ez script, and it sounds wrong.** Amharic yields Ge'ez, which uroman then romanizes with the same scheme as the surrounding text. Tigrinya yields num2words2's own Latin transliteration, which uroman largely passes through — so the words and the numbers reach the model in two different romanization conventions. A native Tigrinya listener judged the resulting audio unintelligible ("I honestly don't know what I just heard").

The two schemes are not close:

```
num2words2 ti : meeraafe seleste gatse arba'a n shew'ate laaye shih n tish'ate mi'ti n semanya n hamushte
Ge'ez → uroman: meeraafe salaseta gatse aarebeaa ne shaweaata laaye shehhe ne tesheaata mieti ne samaaneyaa ne hhaamusheta
```

Every surrounding word (`meeraafe`, `gatse`, `laaye`, `aamate`) is uroman's output, so num2words2's `seleste` / `arba'a` / `mi'ti` are out-of-distribution spellings for a model trained on uroman-romanized text. The standalone ` n ` particles compound it — Tigrinya ን is normally bound to its word, not free-standing.

The fix follows from the cause: emit Tigrinya numbers in **Ge'ez script** and let uroman romanize them like everything else, exactly as the Amharic path already works. num2words2's Tigrinya word choices appear correct — `seleste`=ሰለስተ, `ḥamushte`=ሓሙሽተ, `mi'ti`=ሚእቲ, `shiḥ`=ሽሕ — so what is needed is a script table, not new linguistics. That table has not been verified by a Tigrinya speaker and must be before it ships.

**No configuration produces Ge'ez Tigrinya — the data is not in the package.** Three independent checks:

- The upstream source, `rust/num2words2-core/src/lang_ti.rs`, opens with *"Port of `lang_TI.py` (Tigrinya, transliterated)"* and contains **zero** Ethiopic codepoints in 1382 lines.
- Scanning the compiled `_rust.abi3.so` for Ethiopic-range UTF-8 finds exactly one number-word table, and it is **Amharic** (ዜሮ/አንድ/ሁለት/ሦስት … መቶ/ሺህ/ሚሊዮን, plus ordinals and currency). No Tigrinya Ge'ez words exist anywhere in the binary.
- `script=`, `variant=` and `lang_variant=` all raise `NotImplementedError`; `style="geez"` is silently ignored and still returns `seleste`. `ti_ER` and `ti_ET` are identical to `ti`.

So Tigrinya-in-Ge'ez requires adding a word table to `lang_ti.rs`, not finding a flag.

**A second bug worth carrying into any fork: the billion cliff.** `lang_ti.rs` documents it as a faithfully-reproduced upstream Python bug — `_int_to_word` has no branch above 10⁹ and falls through to `str(number)`. Confirmed, and it affects **Oromo too**:

| n | ti | om | am |
| --- | --- | --- | --- |
| 999,999,999 | words | words | words |
| 1,000,000,000 | `'1000000000'` | `'1000000000'` | `'አንድ ቢሊዮን'` |

For Enisma this is worse than it looks: raw digits returned from the converter would then be stripped by the unsupported-character filter and the number would be silently unread — the exact failure the expansion step exists to prevent. Textbook figures that large are rare, but a defensive check that the converter's output contains no digits is cheap.

The correct words, for whenever a fork gets made: Tigrinya **ሓደ ቢሊዮን** (per a native speaker, parallel to Amharic አንድ ቢሊዮን). For Oromo, *Biliyoona* or *Biliyoona tokko*, and *Kuma tokko* for one thousand — this one came to us second-hand from another assistant and is **not** natively verified, so treat it as a lead rather than a fact.

**Project decision, 2026-09-17:** not worth fixing for v0. Numbers ≥ 10⁹ are vanishingly rare in school textbooks, and the consequence of ignoring the cliff is that such a number is not read aloud — a gap the user can close by typing the number as words in the editor.

End to end, numbers do reach the model once expanded:

```
source : ምዕራፍ 3 ገጽ 47 ላይ 1985 ዓመት ተጻፈ።
now    : meeraafe gatse laaye aamate tatsaafa.
with   : meeraafe sosete gatse arebaa sabaate laaye anede shihe zatanye mato samaaneyaa amesete aamate tatsaafa.
```

## Generation is segmented by sentence punctuation — and the reference recipe destroys that

`OfflineTts.generate` accepts `callback(samples: np.ndarray, progress: float) -> int`, called during generation; returning 0 stops it early. The granularity of that callback is **one utterance**, and sherpa-onnx decides utterances from sentence punctuation in the input text.

The reference recipe strips everything outside `[A-Za-z'\s]`, which removes sentence marks along with the digits. The consequence is larger than it looks. Measured on the same 2000-character Amharic page:

| Input | Utterances | Callback fires | First audio at | Total | Early stop |
| --- | --- | --- | --- | --- | --- |
| Punctuation stripped (reference recipe) | 1 | once, at the end, `progress=1.0` | 90.6 s | 90.6 s | **ignored** — ran to completion |
| `.` retained (14 of them) | 15 | 15 times, incrementally | **7.03 s** | 89.6 s | works — stopped at 16.4 s |

Stripping punctuation turns a page into a single atomic 90-second block with no progress, no partial audio, and no way to cancel. Retaining sentence marks costs nothing in total time (89.6 s vs 90.6 s, inside run-to-run variance) and yields incremental audio, real progress, and working cancellation. The first callback returned 24.7 seconds of audio after 7.0 seconds of work, so playback can start early and stay comfortably ahead of synthesis.

This makes the MMS path structurally similar to Kokoro's, which must chunk anyway for the 510-token limit — both engines can deliver a page as a sequence of sentence-sized pieces rather than one blocking call.

## Kokoro model variants — smaller is worse on CPU, in both directions

Same sentence, same voice, median of 3 runs, plus mean absolute spectral difference against the fp32 output:

| File | Size | Median synth | vs fp32 |
| --- | --- | --- | --- |
| `model.onnx` (fp32) | 326 MB | **1.43 s** | reference |
| `model_fp16.onnx` | 163 MB | 3.13 s | 2.98 dB |
| `model_quantized.onnx` (int8) | 92 MB | 8.93 s | 5.55 dB |
| `model_q8f16.onnx` | 86 MB | **segfault on load** | — |

`model_q8f16.onnx` crashes onnxruntime 1.30.0 with SIGSEGV during `InferenceSession` construction, before inference. The download is not corrupt — the local file's SHA-256 matches HF's LFS oid exactly (`04c658ae…`), as does fp32's (`8fbea51e…`).

The intuition that quantization buys a smaller download at some quality cost does not hold here: on CPU the int8 model is **6.2× slower** than fp32 as well as furthest from it spectrally. Given synthesis time is already the binding UX constraint, fp32 at 326 MB looks like the only sensible choice, and the quantized variants should probably not appear in the download manifest at all. Whether 326 MB is acceptable for first-run download is a separate question this spike does not answer.

Note the spectral figures are a crude FFT-magnitude comparison, adequate to rank the variants and not a substitute for listening. The generated wavs are in the spike scratch directory.

Run-to-run variance on this machine is real but does not disturb the ranking: fp32 on the same sentence measured 1.43 s and 2.16 s as the median-of-3 in two separate process runs. The table uses a single run so the three variants are compared under identical conditions.

## Kokoro's 510-token context forces chunking

`model.onnx` accepts `input_ids` of shape `[1, sequence_length]`, but the style vector is indexed *by token count*: each `voices/<name>.bin` is exactly 522,240 bytes = 510 × 1 × 256 float32, and the documented usage is `ref_s = voices[len(tokens)]`. The usable ceiling is 510 tokens.

A 1473-character English page phonemizes to **1586 tokens** — 3.1× over. Page-length English therefore requires splitting into sentence-aligned chunks and concatenating the audio; the measured page needed 4. Chunk boundaries are audible if chosen badly, so this is a quality-relevant piece of M4, not bookkeeping.

MMS has no such limit in practice: sherpa-onnx accepted 3511 characters as a single utterance and produced coherent, non-silent audio throughout.

## The espeak-ng path-length trap — 159 characters

This one cost the most time and is the most likely to reappear in packaging, so the mechanism is recorded in full.

`kokoro-onnx`'s own documented initialization path fails on this machine:

```
Error processing file '/home/runner/work/espeakng-loader/espeakng-loader/espeak-ng/_dynamic/share/espeak-ng-data/phontab': No such file or directory.
```

The message names the CI machine that built the wheel, which reads as "espeakng-loader is broken". **It is not.** The library and its data are both present and valid. What is measured: past a threshold path length, espeak-ng ignores the data path it is handed and falls back to its compiled-in default — which exists only on the build machine. It then **terminates the process rather than returning an error**, so there is no Python exception, no traceback, and buffered stdout is lost. (The mechanism is almost certainly espeak-ng's fixed-size `path_home` buffer, `N_PATH_HOME` = 160, but that is inferred from the measured boundary — the espeak-ng source was not read.)

Measured directly, by copying the data directory to paths of controlled length:

| Data path length | Result |
| --- | --- |
| ≤ 159 chars | works |
| ≥ 160 chars | hard process exit |

The spike hit it because the scratch venv's data path was 184 characters. A 2×3 cross-test (bundled vs system library × bundled vs system data) isolated it: the bundled library works fine with the system data path, and the system library works fine with the bundled data path — only the long path fails, regardless of which library loads it.

Why this matters beyond the spike: under PyInstaller the sidecar unpacks to a `_MEIxxxxxx` temp directory, and on Windows that sits under the user's profile. A user named with a long account name, or a deep app-data path, can cross 160 characters without doing anything unusual. The failure presents as **"the sidecar died silently"** — no log line, no exception, no non-zero handshake — which is close to the worst possible diagnostic. Any M4 design should stage espeak-ng data at a short, controlled path and assert the length at startup rather than discovering this from a user's crash report.

Cumulative virtualenv size, measured after each install step:

Models are the larger share and are first-run downloads, not bundle: Kokoro fp32 326 MB + 54 voices at 522 KB each (~28 MB for all, or ~2 MB if only English voices ship), plus 114 MB per MMS language, 342 MB for all three. A single-language English project needs ~327 MB; an Amharic project needs ~114 MB.

## Plan premises that need revisiting

**1. misaki is not needed, and is the expensive option.** The plan treats misaki + eSpeak-NG as the recommended English G2P and flags collecting their data files as a bundling risk. In fact `kokoro-onnx` 0.6.1 depends on `espeakng-loader` and `phonemizer`, not misaki — and `espeakng-loader` ships the espeak-ng shared library *and* its full data directory inside the wheel, so there is nothing to collect manually. `misaki[en]` by contrast pulls `spacy` and `spacy-curated-transformers`, and torch behind them. The plan's "verify the exact misaki extras" risk can be retired in favour of the much smaller espeak-only path, at some unquantified quality cost that only listening can settle. The real bundling risk was never the data files — it is the 159-character path limit above.

**2. `uroman` is required, and the model cards are misleading about it.** The MMS repos' READMEs say the character frontend needs "no lexicon or espeak-ng data", which is true and easy to misread as "no preprocessing". The Latin-only symbol tables settle it: Ge'ez must be romanized first. The plan is right to list uroman; it costs almost nothing (`regex` is its only dependency, 7 MB installed).

**3. "TTS romanization quality" is the wrong thing to have flagged as the top risk.** The plan names it the area most likely to need iteration. uroman transliterates Ge'ez cleanly and fast, and Oromo is already Latin. The quality problems that actually showed up are the dropped digits and the chunk-boundary question — neither of which is romanization.

**4. Sample-rate mismatch is real and already visible.** Kokoro emits 24 kHz, MMS 16 kHz, exactly as the plan predicts. Single-language books avoid mixing them within one export, so the plan's mitigation holds — but the preview path has to carry the rate alongside the samples rather than assuming one.

## Digits can be bound to a prefix, and naive expansion breaks the morphology

The corrected Tigrinya fixture exposed a bug in the expansion step. `ብ1985` writes the preposition `ብ-` directly onto the numeral with no space. Replacing `\d+` with `" words "` — spaces included, which is the obvious way to keep the inserted words from fusing with neighbouring text — detaches that prefix:

| Expansion | Result | Reaches the model as |
| --- | --- | --- |
| `" {words} "` (spaced) | `… ብ ሽሕ ን ትሽዓተ …` | `… be shehhe ne tesheaata …` |
| `"{words}"` (in place) | `… ብሽሕ ን ትሽዓተ …` | `… beshehhe ne tesheaata …` |

The spaced form turns a bound morpheme into a standalone word. Substituting in place preserves it, at the cost of losing the guarantee that expanded words stay separated from adjacent text.

**Resolved by listening (2026-09-20): the spaced form is acceptable.** A native Tigrinya speaker judged `ብ ሽሕ ን …` fine to hear, so the bare `" {words} "` substitution stands and no affix-boundary rule is needed for v0. The finding is kept on record because the *input* side is real — textbooks do write `ብ1985` with the prefix attached, and any future change to how numbers are substituted has to keep clearing this case rather than assuming digits are always space-delimited.

## MMS synthesis is not deterministic

The same text synthesized three times produced 2.518 s, 2.759 s and 2.551 s of audio, differing in both length and samples. This is VITS's stochastic duration predictor, not a bug.

Two consequences for M4/M5. Cached audio cannot be validated by re-synthesizing and comparing — freshness has to be tracked as metadata (source text, voice, rate) rather than derived from the audio. And a page re-converted after an edit will differ audibly from the previous take even in the parts that did not change, so "re-convert" is always a whole-page operation from the listener's point of view.

## What this spike did not establish

- **Nothing about the sidecar.** Everything here ran in a bare venv. The webview → Rust → sidecar path is still unexercised beyond `/health`, and streaming ~90 seconds of audio over it is untested.
- **Nothing under PyInstaller.** All measurements are from an unfrozen venv. The frozen binary is where the espeak path-length trap and onnxruntime's data files will actually bite.
- **No real Amharic, Tigrigna or Oromo textbook prose.** The M3 spike flagged that no such PDF exists on this machine; that is still true. The fixtures here are Enisma's own UI strings — real script, real mixed Latin/Ge'ez runs, but not textbook prose and not textbook vocabulary. The page-length Amharic figure repeated those strings to reach 2000 characters.
- **No listening judgement.** Every quality claim here is a number. Whether af_heart reading a biology page is pleasant for hours, whether the MMS voices are intelligible to a native speaker, and whether chunk seams are audible are all open.
- **No GPU measurements**, deliberately — the app targets CPU-only machines.
